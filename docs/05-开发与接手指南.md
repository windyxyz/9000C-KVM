# 05 · 开发与接手指南

> 本文档面向后续接手的人：交付物在哪、整条流水线怎么复现、定制点原理、验证方法论、已知边界。
> 所有专有二进制不入仓库；本仓库只有文档与脚本。

## 1. 交付物与位置（接手第一件事）

| 位置 | 内容 | 说明 |
|---|---|---|
| `9000C\` | **装机套件**：定制版宿主镜像 gz、去遥测安装器 deb、info.json、md5.txt | 直接可用于装机 |
| 本地工作区 `9000c 引导\` | 原版镜像/安装器（备份）、分析提取物 `extracted/`、分析脚本 `_tools/`、本仓库克隆 `9000C-KVM/` | 原件勿删，是 repatch 的输入 |

## 2. 全流程（官方新版 → 装机）

```
官方分发gz（原版）
   │  scripts/repatch-official.sh <官方.gz> <输出目录>
   ▼
定制版镜像 -patched.img.gz
   │  scripts/final-verify.sh（30 项终检，更新头部哈希记录后运行）
   ▼
终检 ALL_PASS
   │  scripts/installer-telemetry-patch.py <官方安装器deb> <输出.deb>
   ▼
装机套件（镜像 + 安装器 + info.json + md5.txt）
   │  在 UOS/麒麟宿主上用安装器离线安装（选定制版镜像 + Windows 模板）
   ▼
重启 → GRUB 进宿主 → 自启动服务自动导入模板 → 全屏 Windows
```

### 流水线内部步骤（repatch-official.sh）

1. 解压官方 gz → loop 挂载其唯一 ext4 分区；
2. 提取宿主内 QEMU → `generic-patch-qemu.py` 单指令定制补丁 → 换入（原版留 `.orig`）；
3. 安装部署套件到镜像 `/opt/win-vm/`，注册 `windows-vm.service` 自启动；
4. 屏蔽宿主管理服务（`.bak` 保留，可完整恢复）；
5. `privacy-hardening.sh`：hosts 阻断厂商云域名（自动从 terminal.conf 探测）、
   管理地址指向 127.0.0.1、清空构建期日志；
6. pigz 重打包，输出新 md5。

## 3. QEMU 定制补丁原理（generic-patch-qemu.py）

宿主镜像内的 QEMU 为厂商定制构建（stripped）。其启动流程中含一处
"检查→特定退出码退出"的逻辑，会阻止虚机在本部署形态下启动。

补丁方法（跨版本通用）：
1. 全二进制扫描 `MOVZ w0, #<退出码>`（编码 `0x52800000 | N<<5`）且后随 B/BL 的站点；
2. 若**唯一**，反查全二进制所有分支形态（B/BL/B.cond/CBZ/CBNZ/TBZ/TBNZ）跳向该站点的指令；
3. 若跳转源**唯一**且为 `TBZ/TBNZ w0, #31`（符号位测试）形态 → 置 NOP；
4. 任一唯一性不成立 → 脚本自动中止，需人工分析新版机制（不要硬改）。

**为什么无损**：v1.0.9 实测该检查只有一个调用方、返回值只有这一处消费、
被修改指令之后寄存器立即被覆盖。静态反汇编 + qemu-user 动态对照双重验证过。

**版本风险**：官方升级 QEMU 后偏移失效属正常，重跑 repatch 流水线即可；
若官方改用其他退出码或多站点机制，脚本会中止并提示人工分析。

## 4. 验证方法论（final-verify.sh，30 项）

| 层 | 手段 | 防什么 |
|---|---|---|
| 1 gzip CRC | 全归档解压验证 | 传输/打包损坏 |
| 2 GPT | 双镜像分区表解析 | 分区表损坏 |
| 3 e2fsck -fn | ext4 只读全检 | 文件系统损坏 |
| 4 逐字节对照 | 内核/initrd/fstab/固件 vs 原版 | 引导链被误改 |
| 哈希 | QEMU 定制版 + .orig 原版双记录 | 补丁丢失/误替换 |
| 5 服务 | 屏蔽链接 + 自启动 + .bak 完整性 | 恢复通道断裂 |
| 5.5 隐私 | hosts/配置/日志 | 信息外漏 |
| 6 动态 | qemu-user 实跑：定制版与原版行为必须分化 | 静态结论与运行时不符 |

动态对照是关键一环：qemu-user（x86 上跑 aarch64 二进制，`-L` 指向镜像根文件系统
作为库环境）可以让两个 QEMU 真实执行到定制点——原版与定制版必须出现行为分化。

## 5. 已知边界与注意事项

1. **在线更新是禁区**：官方升级包会覆盖定制 QEMU 与服务配置，等于还原全部定制；
   由此镜像内的在线更新入口已被屏蔽。升级 = 官方出新版后重跑 repatch 流水线。
2. **Windows 模板前置条件**：模板须在同构虚拟硬件（virtio 设备 + EDK2 固件）上制作，
   预装 virtio-win 驱动，否则 Windows 内设备无法工作。
3. **GPU 无加速**：详见 `03-虚拟设备与性能.md` 第 4 节——平台无 Windows Mali 驱动、
   集显不可直通、GPU 半虚拟化无 Windows 客户机驱动，三条路均堵，属硬件与生态边界。
4. **宿主管理服务被屏蔽**（`.bak` 可恢复）：屏蔽是为了避免其界面对虚机启动流程的干扰；
   恢复后即可回到原始行为。
5. **磁盘空间**：导入模板峰值需约 2 倍虚拟盘大小；D 盘等空间紧张的盘提前清理。

## 6. 本地分析资源索引（不在仓库内）

- `extracted/`：安装器全量脚本、镜像 /boot 与 initrd 提取、thinboot GRUB 配置、
  镜像内 QEMU 原版二进制、宿主服务主程序、分析日志 —— 深入分析时的原始材料
- `_tools/`：一次性分析脚本（镜像挂载、QEMU 交叉引用扫描、动态对照测试、
  构建/验证流水线的开发版）
- 权威结论文档：工作区《引导分析报告.md》《分析进度.md》

## 7. 接手清单

1. 通读 `01~04` 文档建立架构认知；
2. 对照本文档第 1 节清点本地交付物；
3. 用 `final-verify.sh` 复核现有定制镜像是否仍可信；
4. 官方出新版时：下载官方 gz → `repatch-official.sh` → `final-verify.sh` → 替换装机套件；
5. 任何异常先看虚机日志（`/var/log/win-vm.log`、宿主 `vmmanager.log`），
   再用救援模式（启动脚本第 4 参数=1）二分定位。
